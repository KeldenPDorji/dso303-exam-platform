# Exam peak and loss of one Availability Zone

**Exam peak.** 3,000 students starting within 5 minutes is about 10 exam starts per second, then about 100 autosaves per second (3,000 ÷ 30 s). CloudFront serves the single-page app from edge caches, so the page-load burst never reaches the region. API Gateway and Lambda scale per request: Lambda can add 1,000 concurrent executions every 10 seconds, while this load needs about 20 (120 requests/s × 150 ms). In exam week the pipeline sets provisioned concurrency on the API alias, so nobody waits for a cold start. RDS Proxy multiplexes those executions onto a small pool of database connections, so the burst cannot overload PostgreSQL. Each autosave is one idempotent single-row UPDATE, so retries are safe. Work that can wait is queued: the 3,000 submissions at the deadline go to SQS and are marked at capped concurrency, and emails drain at SES's sending rate. API Gateway throttling and a WAF per-IP rate limit (set high, because a whole exam hall can share one NAT address) stop floods without blocking students.

**Loss of one Availability Zone.** Every tier runs in both AZs. CloudFront, S3, SQS, SES, Cognito and API Gateway are regional services spanning AZs. Lambdas run in private subnets in both AZs and continue in the healthy one. Each AZ has its own NAT gateway and route table, so outbound calls never depend on the failed AZ. RDS Multi-AZ replicates every commit synchronously to a standby in the second AZ. If the primary's AZ fails, RDS promotes the standby in about 60–120 seconds with no committed data lost, and RDS Proxy reconnects to it on the same endpoint. During that window the browser keeps answers in local storage and retries, so students lose nothing. Recovery is automatic, well inside the 1-hour RTO.
